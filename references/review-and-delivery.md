# 审稿与交付

用于全文内容终审、按意见逐步修复、文件写回与长任务交接。严格意味着判断有依据，不意味着必须不断提出新问题。

## 1. 先确认正在审查什么

读取实际目标文件和已接受的意见；用户手动修改过时重新读取相应内容。区分内容审查、资料核验、脚注校对和版式检查，不将尚未进行的工作说成已经通过。

当“已经同意的文字”与“文件中现有文字”不同，列明差异及状态。按用户的当前任务处理，不因为旧稿仍在文件里就恢复旧结论，也不把确认文稿的行为当成完成保存。

## 2. 按实质影响审查

优先检查：

1. **一致性**：研究问题、中心论点、各章分析和结语是否在同一主线上？
2. **论证完整性**：关键结论是否缺少中间机制？是否将相关性、可能性或个案推成确定因果与普遍结论？
3. **法律准确性**：主体、权利对象、阶段、适用条件和责任是否对应？建议能否回应已经识别的风险？
4. **证据与贡献**：案例实际证明什么？fight 是否有依据？贡献是否由正文形成？
5. **组织与语言**：是否存在功能重复、标题失配、句段脱节、术语漂移和难以首读理解的表达？

即使脚注留待补齐，影响中心结论的事实或法律依据缺口仍应指出；将它与纯格式问题分开，不要求本轮完成用户已经延后的全部引注工作。

每条意见说明位置、具体问题、为何影响论证以及可操作的修复办法。区分必须修复与可选润色；认可已经成立的部分，不为了凑数或制造严格感添加意见。没有必要的量化标准时，不给武断分数。

## 3. 让审稿意见形成闭合

对多轮修订，可以在项目工作目录维护一份精简记录；已有记录就沿用，不另造多套：

| 项目 | 记录内容 |
| --- | --- |
| 当前依据 | 目标文件、版本、中心论点、本轮范围 |
| 待处理意见 | 位置、问题、预期修复结果 |
| 已处理内容 | 已讨论、已确认、已写入、已核验分别记录 |
| 不再恢复的写法 | 仅记会造成实质回退的否定意见 |
| 下一步 | 当前完成点和下一个明确任务 |

简单任务无需专门建表。交接记录保存判断和状态，不复制整段聊天历史；不未经请求改写全局记忆。

按依赖顺序修复：上游机制或权利基础变化时，再检查下游法律工具；正文稳定后，再统一摘要、引言、结语。不要对全部文字同时进行无边界重写。

修复一处后，检验原意见是否解决，以及相邻内容是否产生新重复或断裂。只有存在新证据、未解决的问题或实质回退时才重开已完成意见。

## 4. 写回与核验

- 用户要求在副本修改时，确定唯一工作副本并沿用；保留原稿。没有要求每轮另存时，避免生成难以辨认的大量版本。
- 写入前确认文件仍是刚刚读取的版本。发现用户同期修改时，读取变化并保留其修改；无法确定的实质冲突单独说明，不能用旧快照覆盖。
- 有明确写回授权就完成操作，无需再次请求常规确认。仅讨论稿件时交付修订建议，并准确说明尚未写回。
- 修改 DOCX 时保留段落样式、真实脚注、注释锚点和其他未要求改变的内容。不要以整篇重建的方式无意丢失文档结构。
- 外文文献按用户及目标期刊要求保留原文题名、作者与来源，不擅自用自译题名替代。具体规则、条款与出处进入真正的脚注，不能把正文括号冒充脚注。
- 保存后重新读取，核对目标修改和范围，确认排除部分保持原样。涉及布局、脚注或完整文件交付时，检查渲染页；无法完成某项检查时如实说明。
- 用户要求打开修改稿时，打开最终保存的文件，并给出可点击路径。文件已打开、内容已保存、版式已核验是不同状态。

具体文件处理使用当前环境中合适的文档工具；本流程不要求固定软件或重做既有排版。

## 5. 完成的判断

本轮约定的问题已处理，修改没有引入实质冲突，交付状态已经说明，就可以结束。若内容已达到可用标准，明确说出这一判断及仍被用户延后的事项。

不把个人措辞偏好升级为新的审稿缺陷，不因工具或检查可用就扩大范围。用户宣布定稿或暂停时停止继续改稿；之后的新任务以新的明确请求为起点。
